# Interactive primitives and composer audit (Phase 15, INV-47, INV-48)

Every interactive surface built up to Phase 14b, checked against the Phase 7 decision record (`ARCHITECTURE.md`, "Interactive primitives: decision record"). Each surface was checked for:

- accessible name and role
- where focus goes on open, roving focus and typeahead
- Escape, the focus trap and focus return
- outside click, nested portals, collision positioning
- touch and keyboard, RTL, and test coverage

Checks run with axe-core 4.14 (WCAG 2.0/2.1/2.2 A and AA rules) and Playwright in Chromium. Colour contrast is listed for Phase 18 and is not a gate here.

**Result:** no primitive had to be replaced. Eight defects were fixed in place (below). No new component framework was added. The only new dependency is the dev-only `@axe-core/playwright`.

Also verified, with no defect found:

- A modal makes everything outside it `aria-hidden`, blocks pointer events and locks scroll.
- Closing a modal by Escape, by Back (a URL overlay unmounting with its route) or by navigating from inside it leaves no `aria-hidden`, `inert`, `pointer-events` or scroll lock behind, and no orphaned popper.
- Opening and closing menus, the search dialog and Settings repeatedly leaves one live-region pair and no extra portals.
- Menus stay inside a 390 × 844 phone screen.

## Primitives retained, with reasons

- **Radix** (Dialog, AlertDialog, DropdownMenu, Tooltip): each passes every check above. The four packages are shared by all surfaces, and their CSS is ChatUI's own.
- **Custom slash listbox:** a Radix menu would take focus from the textarea and so break typing the filter. A custom listbox with `aria-activedescendant` keeps focus in the textarea.
- **Native toasts:** two live regions are all that is needed. A toast library would add a queue, focus behaviour and markup without a requirement for any of them.
- **Native form controls** (switches as checkboxes, selects, file input): accessible without extra code, and they bring the platform pickers on phones.

## Composer (INV-48)

- **Native textarea retained.** A ProseMirror/Tiptap editor is **out of scope**. No approved requirement exists for structured input, inline attachments, mentions or WYSIWYG. Rich paste (below) turns formatting into Markdown text, so it needs no editor.
- **Behaviour covered by tests:**
  - Enter sends; Shift+Enter adds a new line.
  - Enter that ends an IME composition never sends (jsdom and a real Chromium composition over CDP).
  - Two Enters plus a click in the same task store exactly one message (textarea cleared synchronously; `sending` guard).
  - Pasted files attach; pasted rich text becomes Markdown; plain text is left to the browser.
  - Focus stays in the composer through a streamed reply, and text typed during the stream is kept.
  - Drafts are kept per chat; send stays disabled until hydration and a valid model.
  - The modality warning shows before send (the server checks again).
- **Think:**
  - A pill next to + that toggles reasoning (`aria-pressed`, on by default, kept for the tab).
  - Shown only when the selected model has the `reasoning` capability.
  - Sends and regenerations carry `think`. The server passes it on only for reasoning models, as `chat_template_kwargs.enable_thinking`. That field is **UNVERIFIED** against a live server (`docs/provider-notes.md`).
- **Dictation:**
  - A microphone toggle (`aria-pressed`), shown only where the browser has speech recognition.
  - Finished phrases are inserted at the caret.
  - The first use says that the browser's recognition may send the audio to its vendor; ChatUI never receives the audio.
  - A refused microphone, silence and failures are explained in a toast.
- **Rich paste** (`app/chat/html-to-markdown.ts`):
  - Clipboard HTML is parsed into an inert DOMParser document. Headings, emphasis, links (http, https and mailto only), lists, quotes, code and tables become Markdown, and everything else is dropped.
  - The Markdown is inserted through the editing commands, so Undo removes it.
  - Plain HTML without structure, code-editor HTML (whitespace-preserving markup) and anything over 1 MB paste as plain text, as does Ctrl/⌘+Shift+V.

The converter stays in the critical chunk on purpose. A paste handler must decide synchronously whether to cancel the browser's own paste, so a lazily loaded converter would make the first rich paste behave differently from later ones.
